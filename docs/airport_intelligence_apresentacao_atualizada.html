01 · PROBLEMA

Porque faz sentido este projeto?

Os dados necessários para analisar o desempenho dos voos estão distribuídos por fontes diferentes, com estruturas e formatos distintos.

✈

Voos

Contêm informação sobre a companhia, origem, destino, horários e atrasos, conforme os campos disponíveis.

⌖

Aeroportos

Permitem identificar cada aeroporto e conhecer a sua localização geográfica.

☁

Meteorologia

Acrescenta informação sobre as condições existentes num local e numa hora.

Problema a resolver: como reunir e uniformizar estes dados para conseguir analisá-los em conjunto, em vez de consultar cada fonte separadamente?
PROBLEMA02 / 07
02 · OBJETIVO

O que pretendo alcançar?

Objetivo principal
Desenvolver um processo ETL que leia três ficheiros de formatos diferentes, trate e relacione os dados, carregue-os numa base de dados e apresente os resultados num dashboard.

Objetivos específicos

  • Recolher os dados necessários a partir de fontes públicas.
  • Uniformizar datas, tipos de dados e códigos de aeroportos.
  • Tratar valores em falta e registos duplicados.
  • Relacionar voos, aeroportos e meteorologia quando existir correspondência.
  • Carregar os dados tratados no PostgreSQL.

O que quero conseguir analisar

  • Número total de voos incluídos no conjunto de dados.
  • Atraso médio e percentagem de voos atrasados, se os campos permitirem.
  • Comparação por companhia aérea e aeroporto.
  • Evolução dos atrasos ao longo do período selecionado.
  • Possível associação entre condições meteorológicas e atrasos.

O âmbito inicial será limitado às partidas de Atlanta (ATL) durante janeiro de 2025. O ficheiro de aeroportos incluirá ATL e os destinos identificados nos voos; a meteorologia será recolhida inicialmente para Atlanta.

04 · EXTRAÇÃO E TRATAMENTO

Como vou executar o ETL?

E

Extração

1. Descarregar um período limitado de voos históricos.

2. Obter os aeroportos relevantes e convertê-los para XML.

3. Consultar a API meteorológica e guardar a resposta JSON.

4. Registar as fontes, o período e os campos obtidos.

T

Tratamento

1. Ler CSV, JSON e XML no KNIME.

2. Uniformizar nomes, datas, horas e tipos de dados.

3. Tratar valores em falta e duplicados.

4. Validar códigos e relacionar os conjuntos de dados.

5. Calcular indicadores de atraso quando possível.

L

Loading / Carregamento

1. Criar a base de dados e as tabelas no PostgreSQL.

2. Carregar os dados tratados pelo KNIME.

3. Verificar contagens, chaves e registos sem correspondência.

4. Comparar resultados com consultas SQL de validação.

06 · VIABILIDADE E CONCLUSÃO

Porque é um projeto atingível?

Âmbito controlado

  • Começar com um mês de dados e poucos aeroportos.
  • Validar os ficheiros antes de construir todo o workflow.
  • Fazer primeiro uma integração básica e acrescentar a meteorologia depois.
  • Usar ferramentas adequadas a cada fase, sem desenvolver uma aplicação de raiz.

Como vou validar o trabalho?

  • Confirmar que os três ficheiros são lidos corretamente.
  • Verificar tipos, valores em falta e duplicados.
  • Medir quantos voos conseguem ser associados a aeroportos e meteorologia.
  • Comparar os indicadores do dashboard com consultas SQL.
Conclusão: o projeto demonstra, de ponta a ponta, como dados heterogéneos podem ser extraídos, tratados, integrados e carregados para apoiar a análise do desempenho dos voos.

O primeiro passo será validar o ficheiro de voos e selecionar um período compatível com os restantes dados. Só depois fecharei o modelo de dados e os indicadores finais.

Limitação a reconhecer: uma associação entre meteorologia e atrasos não prova que o tempo seja a causa do atraso. O projeto procura explorar padrões, não demonstrar causalidade.
